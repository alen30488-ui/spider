7 частых уязвимостей Telegram-ботов и как их закрыть

Утечка токена, открытый вебхук, админка без проверки прав, подмена сумм оплаты и непроверенный initData в Mini App — разбираем 7 частых уязвимостей Telegram-ботов с примерами кода и чек-листом.

Бот выглядит простым: несколько команд, кнопки, иногда оплата. Но за ним стоят сервер, база данных и токен с полным доступом к аккаунту бота. Большинство проблем, которые мы находим на аудитах, повторяются из проекта в проект. Вот семь самых частых — с объяснением, чем они опасны, и примерами исправлений.

1. Токен бота лежит в коде

Токен — это ключ от бота. С ним можно отправить сообщение от имени бота всем его пользователям, переназначить вебхук на свой сервер и получать все новые сообщения, которые пишут боту. Чаще всего токен утекает через репозиторий: его удаляют из кода, но он остаётся в истории коммитов. Реже — через логи, скриншоты, переписку с подрядчиками и код Mini App, который видит любой пользователь.

Как закрыть:

  • храните токен в переменных окружения или хранилище секретов, а файл .env добавьте в .gitignore;
  • проверьте историю Git — удалённый из кода токен остаётся в старых коммитах;
  • никогда не передавайте токен во фронтенд Mini App;
  • если токен мог утечь, выпустите новый в @BotFather командой /revoke — старый перестанет работать.
import os
BOT_TOKEN = os.environ["BOT_TOKEN"]  # не строкой в коде

2. Вебхук принимает запросы от кого угодно

Если бот получает обновления через вебхук, Telegram отправляет их POST-запросами на ваш адрес, например https://example.com/tg/webhook. Узнав адрес, злоумышленник может прислать туда поддельное обновление от имени любого пользователя — в том числе администратора.

Как закрыть: при вызове setWebhook передайте параметр secret_token. Telegram будет присылать его в заголовке X-Telegram-Bot-Api-Secret-Token каждого запроса, а сервер должен отклонять запросы без него. Заодно уберите токен бота из адреса вебхука — адреса попадают в логи прокси и балансировщиков.

import hmac
def is_telegram(request) -> bool:
    got = request.headers.get("X-Telegram-Bot-Api-Secret-Token", "")
    return hmac.compare_digest(got, WEBHOOK_SECRET)
# в обработчике: if not is_telegram(request): return 403

3. Админ-команды без проверки прав

Команды /admin, /broadcast или /export часто «спрятаны»: их нет в меню, и разработчик надеется, что о них никто не узнает. Но любой пользователь может отправить боту любую команду. Вторая частая ошибка — проверять администратора по username: его можно сменить, а освободившееся имя займёт другой человек.

Как закрыть:

  • проверяйте права в каждом обработчике, а не только в меню;
  • сравнивайте числовой user_id (from.id) — он не меняется;
  • храните список администраторов в настройках или базе, а не в коде;
  • записывайте действия администраторов в журнал.
ADMINS = {123456789, 987654321}  # числовые id, не username
async def broadcast(message):
    if message.from_user.id not in ADMINS:
        return  # молча игнорируем
    ...

4. Бот верит кнопкам и суммам оплаты

Кнопки inline-клавиатуры передают боту строку callback_data. Её создаёт бот, но обрабатывать её нужно как любой пользовательский ввод: если в ней лежит order:1042, проверьте, что заказ 1042 принадлежит именно этому пользователю. Цены, скидки, роли и признак «оплачено» в callback_data хранить нельзя.

С оплатой ошибок ещё больше: бот выдаёт товар по кнопке «Я оплатил», берёт цену из Mini App или не сверяет сумму счёта с заказом. Правильная схема для Telegram Payments:

  1. Сумму и состав заказа бот берёт из своей базы, а не от клиента.
  2. В invoice_payload кладётся номер заказа.
  3. На pre_checkout_query бот сверяет заказ, пользователя, валюту и сумму и отвечает answerPreCheckoutQuery — на это у него 10 секунд.
  4. Товар выдаётся только после сообщения successful_payment, а telegram_payment_charge_id сохраняется, чтобы один платёж не засчитали дважды.
async def on_pre_checkout(query):
    order = await db.get_order(query.invoice_payload)
    ok = (order is not None
          and order.user_id == query.from_user.id
          and order.status == "new"
          and query.currency == order.currency      # "XTR" для Telegram Stars
          and query.total_amount == order.amount)
    await bot.answer_pre_checkout_query(
        query.id, ok=ok,
        error_message=None if ok else "Заказ изменился, оформите его заново")

5. Mini App не проверяет initData на сервере

Mini App получает данные пользователя от Telegram в двух видах: строкой Telegram.WebApp.initData и объектом initDataUnsafe. Частая ошибка — отправить на сервер user.id из initDataUnsafe и поверить ему. Подделать такой запрос можно за минуту: достаточно открыть Mini App в браузере и поменять id.

Как закрыть: передавайте на сервер строку initData целиком и проверяйте её подпись. Секретный ключ — HMAC-SHA256 от токена бота с ключом WebAppData, а подпись — HMAC-SHA256 от отсортированных полей (кроме hash) в формате key=value, разделённых переводом строки. Дополнительно проверяйте auth_date, чтобы не принимать старые данные.

import crypto from 'node:crypto';
export function checkInitData(initData, botToken, maxAgeSec = 3600) {
  const params = new URLSearchParams(initData);
  const hash = params.get('hash') || '';
  params.delete('hash');
  const dataCheckString = [...params]
    .sort(([a], [b]) => (a < b ? -1 : 1))
    .map(([k, v]) => `${k}=${v}`)
    .join('\n');
  const secret = crypto.createHmac('sha256', 'WebAppData').update(botToken).digest();
  const calc = crypto.createHmac('sha256', secret).update(dataCheckString).digest('hex');
  const fresh = Date.now() / 1000 - Number(params.get('auth_date')) < maxAgeSec;
  return fresh && hash.length === calc.length
    && crypto.timingSafeEqual(Buffer.from(hash), Buffer.from(calc));
}

Всё, что приходит из Mini App помимо подписанного initData — цены, корзина, статус подписки, — тоже проверяйте на сервере. Код Mini App работает на устройстве пользователя, и изменить его может любой.

6. Инъекции и небезопасная работа с файлами

Всё, что присылает пользователь — текст, имя файла, ссылка, — может оказаться атакой:

  • SQL-инъекции. Если запрос к базе собирается склейкой строк, сообщение пользователя может изменить сам запрос. Используйте параметризованные запросы или ORM.
  • HTML в сообщениях. Если бот пересылает текст пользователя с parse_mode=HTML, экранируйте его — иначе в сообщении появятся чужие ссылки и форматирование.
  • Файлы. Проверяйте тип и размер, не сохраняйте файл под именем от пользователя — имя вида ../../config.py может перезаписать файлы приложения.
  • Ссылки. Бот, который «скачивает файл по ссылке», не должен ходить на внутренние адреса вроде http://localhost или 169.254.169.254 — это SSRF, через которую добираются до внутренней сети и секретов облака.
# плохо: текст пользователя попадает прямо в SQL
cur.execute(f"SELECT * FROM orders WHERE id = {text}")
# хорошо: параметризованный запрос
cur.execute("SELECT * FROM orders WHERE id = %s", (text,))

7. Нет защиты от флуда, а в логах — персональные данные

Без ограничений один пользователь может завалить бота тысячами запросов. Бот упрётся в лимиты Telegram — около 30 сообщений в секунду на всех пользователей и примерно одно сообщение в секунду в один чат — и перестанет отвечать остальным. Если бот обращается к платным API, например к нейросетям, флуд сожжёт и бюджет.

Отдельная проблема — логи. Бот пишет в журнал всё подряд: телефоны, адреса, номера заказов, а иногда и токены. Логи хранятся годами, уходят в сервисы мониторинга и доступны многим сотрудникам. Для российских проектов это ещё и вопрос соблюдения 152-ФЗ «О персональных данных».

Как закрыть:

  • ограничьте частоту запросов от одного пользователя и длину сообщений;
  • отправляйте рассылки через очередь и соблюдайте паузу из retry_after, когда Telegram отвечает ошибкой 429;
  • маскируйте телефоны, e-mail и токены в логах и задайте срок их хранения;
  • храните персональные данные только там, где они действительно нужны, и ограничьте к ним доступ.

Чек-лист для самопроверки

  1. Токен хранится в переменных окружения и никогда не попадал в Git.
  2. Вебхук проверяет заголовок X-Telegram-Bot-Api-Secret-Token.
  3. Права администратора проверяются по user_id в каждом обработчике.
  4. Суммы и товары сверяются на сервере в pre_checkout_query, а доступ выдаётся только после successful_payment.
  5. Сервер проверяет подпись initData и auth_date для каждого запроса из Mini App.
  6. Запросы к базе параметризованы, файлы и ссылки от пользователей проверяются.
  7. Есть ограничение частоты запросов, а в логах нет персональных данных и токенов.

Если хотя бы один пункт вызывает сомнения, а бот принимает оплату, хранит данные клиентов или управляет чем-⁠то важным, — стоит провести аудит. Мы проверяем код, инфраструктуру и сценарии бота и Mini App вручную и с помощью сканеров, по итогам отдаём отчёт с уровнями риска и рекомендациями, а после исправлений проверяем повторно.
