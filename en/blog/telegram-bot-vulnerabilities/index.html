7 common Telegram bot vulnerabilities and how to fix them

A leaked token, an open webhook, admin commands without checks, tampered payment amounts and unverified initData in Mini Apps — the 7 most common Telegram bot vulnerabilities with code examples and a checklist.

A bot looks simple: a few commands, some buttons, maybe payments. But behind it there is a server, a database and a token with full access to the bot account. Most of the issues we find in audits repeat from project to project. Here are the seven most common ones — why they are dangerous and how to fix them.

1. The bot token lives in the code

The token is the key to your bot. With it, anyone can message all of the bot’s users on its behalf, point the webhook to their own server and receive every new message sent to the bot. Most often the token leaks through the repository: it is removed from the code but stays in the commit history. Less often it leaks through logs, screenshots, chats with contractors or Mini App code that every user can see.

How to fix it:

  • keep the token in environment variables or a secrets manager, and add .env to .gitignore;
  • check your Git history — a token removed from the code stays in old commits;
  • never send the token to the Mini App frontend;
  • if the token may have leaked, issue a new one with the /revoke command in @BotFather — the old one stops working.
import os
BOT_TOKEN = os.environ["BOT_TOKEN"]  # not a string in the code

2. The webhook accepts requests from anyone

If the bot receives updates via a webhook, Telegram sends them as POST requests to your URL, for example https://example.com/tg/webhook. Anyone who learns the URL can send a forged update on behalf of any user — including an admin.

How to fix it: pass the secret_token parameter when calling setWebhook. Telegram will send it in the X-Telegram-Bot-Api-Secret-Token header of every request, and your server should reject requests without it. While you are at it, remove the bot token from the webhook URL — URLs end up in proxy and load balancer logs.

import hmac
def is_telegram(request) -> bool:
    got = request.headers.get("X-Telegram-Bot-Api-Secret-Token", "")
    return hmac.compare_digest(got, WEBHOOK_SECRET)
# in the handler: if not is_telegram(request): return 403

3. Admin commands without permission checks

Commands like /admin, /broadcast or /export are often “hidden”: they are not in the menu, and the developer hopes nobody finds them. But any user can send any command to a bot. The second common mistake is checking admins by username: it can be changed, and a freed-up username can be taken by someone else.

How to fix it:

  • check permissions in every handler, not just in the menu;
  • compare the numeric user_id (from.id) — it never changes;
  • keep the admin list in settings or the database, not in the code;
  • log every admin action.
ADMINS = {123456789, 987654321}  # numeric ids, not usernames
async def broadcast(message):
    if message.from_user.id not in ADMINS:
        return  # silently ignore
    ...

4. The bot trusts buttons and payment amounts

Inline keyboard buttons send the bot a callback_data string. The bot creates it, but you should treat it like any other user input: if it contains order:1042, check that order 1042 belongs to this very user. Never store prices, discounts, roles or a “paid” flag in callback_data.

Payments have even more pitfalls: the bot delivers the goods when the user taps “I have paid”, takes the price from the Mini App or does not compare the invoice amount with the order. The correct flow for Telegram Payments:

  1. The bot takes the amount and order contents from its own database, not from the client.
  2. The order number goes into invoice_payload.
  3. On pre_checkout_query, the bot checks the order, the user, the currency and the amount and replies with answerPreCheckoutQuery — it has 10 seconds to do so.
  4. The goods are delivered only after the successful_payment message, and telegram_payment_charge_id is stored so the same payment is never counted twice.
async def on_pre_checkout(query):
    order = await db.get_order(query.invoice_payload)
    ok = (order is not None
          and order.user_id == query.from_user.id
          and order.status == "new"
          and query.currency == order.currency      # "XTR" for Telegram Stars
          and query.total_amount == order.amount)
    await bot.answer_pre_checkout_query(
        query.id, ok=ok,
        error_message=None if ok else "The order has changed, please place it again")

5. The Mini App does not verify initData on the server

A Mini App receives user data from Telegram in two forms: the Telegram.WebApp.initData string and the initDataUnsafe object. A common mistake is to send user.id from initDataUnsafe to the server and trust it. Forging such a request takes a minute: open the Mini App in a browser and change the id.

How to fix it: send the whole initData string to the server and verify its signature. The secret key is an HMAC-SHA256 of the bot token with WebAppData as the key, and the signature is an HMAC-SHA256 of all fields except hash, sorted alphabetically as key=value lines separated by line breaks. Also check auth_date so you do not accept stale data.

import crypto from 'node:crypto';
export function checkInitData(initData, botToken, maxAgeSec = 3600) {
  const params = new URLSearchParams(initData);
  const hash = params.get('hash') || '';
  params.delete('hash');
  const dataCheckString = [...params]
    .sort(([a], [b]) => (a < b ? -1 : 1))
    .map(([k, v]) => `${k}=${v}`)
    .join('\n');
  const secret = crypto.createHmac('sha256', 'WebAppData').update(botToken).digest();
  const calc = crypto.createHmac('sha256', secret).update(dataCheckString).digest('hex');
  const fresh = Date.now() / 1000 - Number(params.get('auth_date')) < maxAgeSec;
  return fresh && hash.length === calc.length
    && crypto.timingSafeEqual(Buffer.from(hash), Buffer.from(calc));
}

Everything else that comes from the Mini App besides the signed initData — prices, the cart, the subscription status — must be validated on the server too. Mini App code runs on the user’s device, and anyone can modify it.

6. Injections and unsafe file handling

Anything a user sends — text, a file name, a link — can be an attack:

  • SQL injection. If a database query is built by concatenating strings, a user’s message can change the query itself. Use parameterized queries or an ORM.
  • HTML in messages. If the bot forwards user text with parse_mode=HTML, escape it — otherwise foreign links and formatting appear in your messages.
  • Files. Check the type and size, and never save a file under a user-supplied name — a name like ../../config.py can overwrite your application files.
  • Links. A bot that “downloads a file from a link” must not request internal addresses such as http://localhost or 169.254.169.254 — that is SSRF, a way into your internal network and cloud secrets.
# bad: user text goes straight into SQL
cur.execute(f"SELECT * FROM orders WHERE id = {text}")
# good: a parameterized query
cur.execute("SELECT * FROM orders WHERE id = %s", (text,))

7. No flood protection — and personal data in the logs

Without limits, a single user can flood the bot with thousands of requests. The bot hits Telegram’s limits — about 30 messages per second across all users and roughly one message per second per chat — and stops answering everyone else. If the bot calls paid APIs such as AI models, a flood burns through your budget too.

Logs are a separate problem. Bots often log everything: phone numbers, addresses, order numbers and sometimes tokens. Logs are kept for years, shipped to monitoring services and readable by many people. Depending on where your users are, it is also a matter of GDPR or Russia’s personal data law (152-FZ).

How to fix it:

  • limit the request rate per user and the message length;
  • send broadcasts through a queue and wait for retry_after when Telegram replies with error 429;
  • mask phone numbers, e-mails and tokens in logs and set a retention period;
  • keep personal data only where it is really needed and restrict access to it.

Self-check checklist

  1. The token is kept in environment variables and has never been committed to Git.
  2. The webhook checks the X-Telegram-Bot-Api-Secret-Token header.
  3. Admin permissions are checked by user_id in every handler.
  4. Amounts and items are verified on the server in pre_checkout_query, and access is granted only after successful_payment.
  5. The server verifies the initData signature and auth_date for every Mini App request.
  6. Database queries are parameterized, and user files and links are validated.
  7. There is a rate limit, and logs contain no personal data or tokens.

If any item raises doubts, and your bot takes payments, stores customer data or controls something important, it is worth running an audit.
